Chapter 3
METHODOLOGY
This chapter presents the methodology used in developing the Facial Recognition and Attendance Monitoring with Embedded System (FRAMES): A Web-Based System with Hand Gesture Control using Raspberry Pi. It includes the project design—such as the context diagram, top-level data flow diagram, use case diagram, database design, and block diagram—as well as the project development process, system operations and testing procedures, and evaluation approach based on ISO/IEC 25010 standards.
Project Design 
The study will develop a Facial Recognition and Attendance Monitoring with Embedded System (FRAMES): A Web-Based System with Hand Gesture Control using Raspberry Pi to enable students, faculty, and administrators to manage attendance and campus monitoring through an online platform. The System Flowchart, Use Case Diagram, Entity-Relationship Diagram (ERD), and Block Diagram comprise the project design, which illustrates and describes the system's flow and design process.
System Design
System Architecture
Context Data Flow Diagram 
Figure 2 below illustrates the Context Level Data Flow Diagram of the proposed Facial Recognition and Attendance Monitoring with Embedded System (FRAMES). At this level, the system is presented as a single process that interacts with external entities including Students, Faculty, Administrators, Department Heads, and the Raspberry Pi Camera. Each entity exchanges specific inputs and outputs with the system to support attendance monitoring and reporting. The Student entity provides the system with their personal information, facial data, and live facial scans during registration and class attendance. These are processed in real time through the Raspberry Pi camera to confirm the student’s identity. The system, in turn, returns attendance confirmation, real-time status indicators, and personal attendance reports and insights that the student can access as feedback for their attendance record. The Faculty entity similarly provides personal information, facial data, live scans, class schedules, and student master lists into the system. Faculty receive attendance confirmation, class-specific reports and insights, as well as real-time indicators for both their attendance and that of their students. This ensures that the faculty can monitor attendance directly from their dashboard without manually tracking students. The Admin entity plays a supervisory role. Admins send user enrollment requests for both students and faculty, manage camera configurations such as activation, scheduling, and room setup, and oversee the system’s overall setup. The system provides admins with system reports and insights, which summarize the overall usage, attendance patterns, and technical performance of the framework. The Department Head entity is responsible for higher-level oversight. They receive faculty-specific reports generated by the system, which allow them to review and evaluate faculty attendance records and compliance. These reports provide a basis for decision-making and institutional monitoring at the departmental level. The Raspberry Pi Camera entity provides the embedded system capability. It sends captured facial frames and hand gesture data to FRAMES for processing, while also updating the system on facial frame processing and gesture processing statuses. This ensures that the recognition and gesture modules are functioning correctly in real time.
Overall, the Context Level Diagram demonstrates how FRAMES serves as the central hub that connects all key stakeholders and hardware. It integrates the data flow from students and faculty with administrative oversight and hardware support, ensuring that attendance monitoring is accurate, secure, transparent, and supported by real-time reporting.

Top-Level Data flow diagram 
	Figure 3 below shows the Top-Level Data Flow Diagram of the proposed Facial Recognition and Attendance Monitoring with Embedded System (FRAMES). This diagram expands the single process shown in the Context Diagram into six interconnected processes that define how inputs from users and hardware are transformed into useful outputs such as attendance logs, reports, and dashboards.
Process 1.0: System Set-Up. This process manages system configuration and camera management, such as room setup, scheduling, and activation. The admin configures the Raspberry Pi camera and system environment, ensuring that the devices and schedules are properly aligned with institutional requirements. Configuration data is stored in the System Configuration Data (D1) for reference and updates.
Process 2.0: User Registration. Students and faculty submit personal information and facial data, which the admin validates before storage. Admins also send user enrollment requests to the system. The registration process ensures that all users are properly enrolled and linked to the database. Verified and registered users are stored in the User Database (D2).
Process 3.0: Facial Recognition. During attendance, the Raspberry Pi Camera captures live facial scans and converts them into facial frames. These are processed and compared with the registered data in the user database. The system generates a facial frames processing status to indicate successful or failed recognition. Captured facial frames are then validated for identity matching.
Process 4.0: Gesture Recognition. As a spoof-prevention mechanism, the system requires the user to perform a hand gesture after facial recognition. The Raspberry Pi camera captures hand gesture inputs, which are validated against pre-defined gestures stored in the system. Only when both identity and gesture are confirmed is the process considered successful. Unverified identities or failed gestures are flagged.
Process 5.0: Attendance Logging. Once both recognition phases are validated, the system logs the attendance into the User Logs (D3). This includes the timestamp of attendance, identity confirmation, and gesture verification. Attendance confirmation and status indicators are provided to both students and faculty in real time. User insights are stored in User Insights Data (D5), and individual reports are updated in User Reports (D4).
Process 6.0: Report Generation & Dashboards. Processed attendance and activity data are consolidated into reports and visual dashboards. This includes personal attendance reports, class-specific reports, faculty-specific reports, and department-level summaries. Students can view personal logs, faculty can track class-level attendance, and department heads receive faculty compliance reports. Admins have access to system-wide reports and insights for overall monitoring.
Through these six processes, the Top-Level DFD demonstrates how FRAMES integrates real-time recognition, gesture validation, logging, and reporting into a single workflow. The data stores (D1–D5) act as repositories for system configuration, user data, logs, and reports, ensuring secure storage and efficient retrieval.

Project Development
To ensure a systematic and structured approach in the development of FRAMES, the researchers will employ the Waterfall methodology. This sequential model provides a step-by-step framework where each phase must be completed before the next begins. It ensures traceability of deliverables, which is essential for systems requiring accuracy, reliability, and usability. The methodology consists of five phases: Analyze, Design, Create, Test, and Evaluate.
Analyze
In this phase, the researchers will identify and document the functional and non-functional requirements of FRAMES. Real-time attendance monitoring through facial recognition and gesture recognition will be emphasized as core features. The requirements include:
Real-time attendance tracking through facial recognition.
Hand gesture-based authentication for log-in, log-out, break, and return.
Dashboard-driven visualization of attendance and room occupancy.
Feasibility analysis confirms that Raspberry Pi 4 with Pi Camera provides an affordable and scalable hardware platform for processing facial and gesture data.
Design
This phase outlines the architecture, user flows, and database schemas. FRAMES will adopt modularity and role-based access, providing three roles: administrator, faculty, and student.
Key design outputs include:
Wireframes and dashboards for attendance reports, facial registration, and occupancy status.
Room visualization with occupancy indicators (vacant/occupied).
Database schema for storing biometric encodings, gesture logs, and attendance data.
System block diagram illustrating the integration of Raspberry Pi, camera input, recognition modules, and the web-based frontend.

Create
Implementation will focus on integrating the selected technologies. Flask will serve as the backend framework due to its simplicity and compatibility with Raspberry Pi deployment. The frontend will use React.js for an interactive user interface, while MySQL will manage structured data storage.
Facial recognition handled by OpenCV + dlib.
Gesture detection powered by MediaPipe.
Database integration through MySQL to store user profiles, encodings, gesture mappings, and logs.
Web dashboards for real-time visualization of attendance and occupancy.
Gestures will include:
Open palm – log in
Closed fist – log out
Peace sign (two fingers) – break
Thumbs-up – return from break
Test
Testing ensures system accuracy and reliability. Accuracy testing will focus on recognition rates under varying lighting and angles. The following test strategies will be applied:
Unit testing: for facial recognition, gesture detection, and data logging.
Integration testing: to confirm smooth communication between the Raspberry Pi, recognition modules, backend, and dashboards.
System testing: validating real-time attendance logging and room visualization.
User acceptance testing: involving faculty and students, ensuring usability and responsiveness.
Evaluate
Evaluation will be conducted using the ISO/IEC 25010 Software Quality Model. FRAMES will be evaluated in terms of:
Functional suitability: accuracy of face and gesture recognition.
Performance efficiency: real-time updates and processing speed.
Interaction capability (usability): user-friendliness of dashboards.
Reliability: system stability during extended use.
Security: protection of biometric and attendance data.
The TUP Prototype Evaluation Instrument will also be employed to assess the system’s overall usability, practicality, and user perception. It focuses on the following aspects:
Functionality: how well the modules perform their intended tasks.
Aesthetics: visual presentation and layout appeal of the dashboard interface.
Workability: operational efficiency and responsiveness of hardware and software.
Durability: ability of the system and hardware to sustain prolonged or repetitive usage.
Economy: cost-effectiveness of the setup.
Safety: assurance that hardware and data handling pose no risks.
By combining these two evaluation models, FRAMES will be assessed both in terms of technical performance and user-centered acceptability, ensuring that the developed prototype is functional, secure, efficient, and practical for implementation within classroom environments. Feedback from students, faculty, and administrators will provide insights for refinement and future enhancements.



Operations and Testing Procedure 
This section explains how the FRAMES system is set up and used by different people during the testing phase.
System Startup: Users open the web portal using a standard browser like Chrome or Firefox. 
User Login and Role Verification:
Department Head (HEAD): Signs in to check the "Management" tab. They must approve or deny any new faculty sign-ups before those teachers can use the system. 
Faculty: Once approved, teachers log in to manage their classes. They are responsible for uploading the class schedule (PDF), which automatically creates accounts for every student in that class. 
Student: Signs in using the account created by the teacher's schedule upload. 
The Facial Registration Gate: If a user (Faculty or Student) logs in for the first time, the system checks their registration status. If they haven't registered their face, the system blocks the dashboard and sends them straight to the camera page to save their facial data. 
Kiosk Attendance Scans: The Raspberry Pi unit, which includes a camera and a screen, is placed at the classroom door. It scans the faces of people as they enter or leave. 
Using Hand Gestures: After the camera recognizes a face, the person must make a specific hand gesture to confirm their action: 
Open Palm: To log in or enter the room. 
Peace Sign (Two Fingers): To leave for a short break. 
Thumbs-Up: To return from a break. 
Closed Fist: To log out or leave the class for the day. 
Real-Time Monitoring: All logs are sent to the database instantly. Teachers and Heads can see who is currently in the room or on break through a color-coded dashboard. 
Data Export: Faculty and Heads can download attendance summaries and room usage records in PDF or CSV formats for their school files.

Evaluation Procedure 
The evaluation procedure examined the system's overall performance, functionality and user acceptance to establish its accuracy, reliability and efficiency in real-time monitoring and attendance tracking. It aims to comprehensively evaluate the usability and effectiveness of the Facial Recognition and Attendance Monitoring with Embedded System (FRAMES) by actual demonstration along with user-centered evaluations.
The evaluation procedure for acceptable use of the FRAMES will be based on the ISO/IEC 25010 software quality model and the Technological University of the Philippines (TUP) Prototype Evaluation Instrument. These standards evaluate a software product according to the following characteristics: Functional Suitability, Performance Efficiency, Interaction Capability, Reliability, Security, and Usability.
After the system’s development and internal testing, a series of test cases will be conducted to validate its performance.  The TUP Evaluation Instrument will be applied after the application of the system to quantify the system performance in terms of functionality, usability, reliability, efficiency and workability as well as overall acceptance.
The following steps shall be followed to evaluate the acceptance and effectiveness of the proposed FRAMES:
A total of twenty (20) evaluators — composed of students, faculty members, and administrative staff from the College of Science — will be randomly chosen to take part in the system evaluation.
The researchers will start with a short demonstration to show the system’s main features: face recognition and gesture-based attendance, a live room visualization for occupancy monitoring, and a centralized web portal with interactive dashboards for different user roles. 
Each evaluator will be issued role-specific login credentials to allow hands-on exploration. During the evaluation, participants will conduct attendance simulations using facial recognition and gesture authentication, review the web dashboard, and test the monitoring tools to determine overall system performance and user-friendliness.
After the demonstration, the evaluators will complete a structured questionnaire based on the ISO/IEC 25010 quality characteristics and the TUP Evaluation Instrument. The form includes criteria such as functionality, usability, reliability, efficiency, and user experience.
Once accomplished, all questionnaires will be collected and summarized. The data will be processed using Microsoft Excel to compute mean scores and generate the overall ratings for each criterion.
The gathered data will then be interpreted using the Likert Scale, as shown in Table 6. Each item is rated from 1 to 4, depending on how satisfied or in agreement the evaluator is. This scale provides a clear view of how well the system meets user expectations and the set quality standards.
