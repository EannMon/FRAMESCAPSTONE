Chapter 3
METHODOLOGY

This chapter presents the project design, project development, operation and testing procedures, and evaluation procedure.

Project Design
This study followed a developmental-descriptive design. The developmental aspect involves designing and building a web-based Inventory and POS System specifically for Fluff ‘n Stuff by DA Constance — a small pet accessory shop. The descriptive aspect focuses on analyzing and presenting the system’s capabilities, workflows, and output based on testing and user needs. This methodology was chosen because the study’s goal is not only to solve a practical problem but also to document the process in a way that could be replicated by other micro-retailers or future developers with similar business needs. System was designed using standard analysis and modeling tools. A Use Case Diagram was created to visualize the roles (Admin and Cashier) and the actions they can perform in the system. The design emphasizes real-time data synchronization and secure cloud storage, ensuring that inventory, sales transactions, and reports are accessible anytime and anywhere with an internet connection.
The Context Diagram illustrates the external actors interacting with the system, such as the owner and system users, see Figure 2. The Data Flow Diagram (DFD) shows how information (e.g., product data, sales data) flows between modules and processes, see Figure 2.

Figure 2 presents a context diagram of the Fluff ‘n Stuff Inventory with POS System, showing how different users interact with the system as a whole. At the center is the “Inventory System with POS,” which serves as the main platform that processes and manages all transactions and inventory-related activities. Surrounding it are the external entities that communicate with the system: the Owner (Admin), the User Account, and the Cashier.
The Cashier interacts with the system to process customer transactions. The cashier enters order details during a sale, and the system responds by generating the corresponding sales details, such as totals and transaction records. Overall, the diagram clearly illustrates how the system acts as the central hub that connects administrative management and daily sales operations, ensuring that inventory tracking and point-of-sale activities are seamlessly integrated for the business.
At the management level, the owner or admin is responsible for managing the overall system. Through secure login credentials, the owner can input and update product details such as item names, prices, and stock levels. In return, the system generates reports that allow the owner to monitor sales performance and inventory status. On the other hand, the User Account represents authorized users who must log in using a username and password before accessing the system. This ensures that only permitted individuals can operate the platform.

In the Top-Level DFD (Level 1), this single system process is broken down into four major internal processes: Login Management, Inventory Management, POS Transaction, and Report Generation. These processes collectively perform the functions previously represented as one unit in the context diagram.
The Login Management process now handles the username and password data coming from both the Owner (Admin) and the Cashier. This corresponds directly to the authentication flow shown in the context diagram. Instead of authentication being handled by the entire system as one block, it is now clearly assigned to a specific internal process.
The Inventory Management process corresponds to the product details flow from the Owner. In the context diagram, the Owner sends product details to the system. In the Level 1 DFD, those product details are processed by Inventory Management and stored in the Product Table (D1). This makes the internal data storage visible, which was not shown in the context diagram.
The POS Transaction process corresponds to the order details submitted by the Cashier. In the context diagram, the Cashier sends order details and receives sales details from the system. In the Level 1 DFD, the POS Transaction process receives order details from the Cashier, retrieves product details from the Product Table, processes the transaction, and stores the completed transaction in the Sales Table (D2).
The Report Generation process corresponds to the report flow sent to the Owner in the context diagram. Instead of the system directly generating reports as a single block, this responsibility is now assigned to a dedicated process that retrieves sales details from the Sales Table and generates reports for the Owner.
Depicts in Figure 4, the role-based functions of the Fluff ’n Stuff Inventory System with POS, showing how different users interact with the system’s features. The Admin/Owner has overall control and access to major system functions such as inventory management, viewing summary reports, generating reports, managing users, backing up the database, and tracking user action logs. This role ensures that the system is properly maintained and that business data is monitored.

The Cashier Role focuses on sales transactions through the Point of Sale (POS) module. The cashier can process sales, generate receipts, issue refunds, delete transactions, and reprint receipts through the transaction logs. These functions support the daily sales operations of the store.
Meanwhile, the Inventory Role manages the stock and product records. This role allows the user to add, update, or delete product categories, order products, and track or update supply orders. The Supply Order feature helps monitor product restocking, ensuring that inventory levels are properly maintained.
Overall, the figure shows how the system separates responsibilities among the Admin/Owner, Cashier, and Inventory roles, allowing the Fluff ’n Stuff Inventory System with POS to manage sales transactions, product inventory, and business reports efficiently.

Project Development 
The researcher used the Agile Development Life Cycle, divided into the following iterative phases:
1. Requirements Gathering – Identified user needs through interviews and observation of Fluff ‘n Stuff’s current manual process. Key functional requirements included inventory tracking, POS operations, sales reporting, user management, and database backup. The study emphasized role-based access for the Admin, Owner, Cashier, and Inventory Staff.
2. Planning – Created a timeline and sprint backlog for system features to be built. Core modules such as POS and Inventory were developed first, followed by auxiliary modules including Reports, Supply Order, Transaction History, User Logs, and Backup/Restore. Timelines were structured to allow for incremental feedback.
3. Design – Wireframes and mockups were designed to visualize system navigation and workflows. A MongoDB schema was developed to accommodate modules such as product records, sales transactions, supply orders, and user activity logs. Use case diagrams, entity-relationship diagrams, and process flowcharts were created to model user roles and data interactions.
4. Development – The system was built using HTML, CSS, and JavaScript for the frontend interface, with Node.js and Express managing backend logic and routing. MongoDB Atlas served as the cloud-based database, enabling scalable and secure storage of inventory, sales, and user data. CRUD functionalities were implemented for all modules, ensuring that POS operations, inventory management, reporting, and supply orders were fully integrated.
5. System Requirements – The system operates through a web-based interface accessible via modern browsers (e.g., Chrome, Firefox, Edge) and is hosted on a Node.js environment. Role-based access ensures data security, with separate permissions for Admin, Owner, Cashier, and Inventory staff. Manual backup and restore functions are included, enabling downloadable and restorable database snapshots.
6. Testing and Review – Conducted manual testing at the end of each sprint. Checked all CRUD operations, report generation, and role-based access for both admin and cashier users.
7. Deployment and Feedback – The system was deployed in a test environment and evaluated by selected users. Feedback focused on interface clarity, speed of transaction processing, and accuracy of inventory deduction. Refinements were made to the POS module, report formatting, and stock-level alert system to ensure alignment with business workflows.
