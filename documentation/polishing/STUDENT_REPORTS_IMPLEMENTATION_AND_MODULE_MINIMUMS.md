## 1) Student Module: What Is Implemented Now

### 1.1 Active Report Types in Student UI
The student report selector currently exposes these report codes and labels:
- `DAILY_REPORT` - Daily Attendance
- `WEEKLY_SUMMARY` - Weekly Attendance Summary
- `MONTHLY_TRENDS` - Monthly Attendance Trends
- `SEM_REPORT` - Semestral Report
- `LATE_REPORT` - Personal Late Arrival Report
- `BREAK_LOG` - Break Duration Log
- `ABSENT_LOG` - Absent Logs
- `CONSISTENCY` - Personal Consistency Index

Note:
- `HISTORY_30D` is still recognized by backend window parsing but is not exposed in the current Student report dropdown.

### 1.2 Filter and Control Flow (Student)
Control order in the Student page:
1. Report Type
2. Subject Filter
3. Date/Semester controls (dynamic by report)

Behavior rules:
- Weekly summary forces subject filter to `ALL` (All Enrolled Subjects).
- For other report types, subject filter can scope to a specific class if selected.
- Absent logs use semester and school-year picker (not single date).

### 1.3 Date Window Resolution Per Student Report
- `DAILY_REPORT`: one selected day.
- `WEEKLY_SUMMARY`: one selected week inside a selected month.
- `MONTHLY_TRENDS`: one selected month.
- `SEM_REPORT`: semester range from school year + semester selector.
- `LATE_REPORT`: semester range.
- `BREAK_LOG`: semester range.
- `ABSENT_LOG`: semester range.
- `CONSISTENCY`: semester range.

Implementation detail:
- Student UI uses local-date formatting for date boundaries to avoid UTC day-shift issues.

### 1.4 Rows and Data Semantics in Student Reports
Student rows come from server envelope response (`rows`) and include:
- `timestamp`, `action`, `is_late`
- `subject_title`, `room`, `faculty_name`, `remarks`

Supported rendered statuses:
- `ENTERED`
- `LATE`
- `ABSENT`
- `ON BREAK (OUT)`
- `FROM BREAK (IN)`
- `EXITED`

Special logic for absences:
- For `DAILY_REPORT` and `ABSENT_LOG`, backend synthesizes ABSENT rows for conducted sessions where the student has no ENTRY.
- Absent synthesis is schedule-aware and exception-aware:
  - Counts only schedule-aligned conducted sessions.
  - Skips cancelled/holiday/online exceptions.

### 1.5 Analytics and Insight Panels (Student)
Student report response contains:
- `summary_metrics`
- `insights`
- `session_count_reference`

Analytics visibility in UI is intentionally limited to:
- `WEEKLY_SUMMARY`
- `MONTHLY_TRENDS`
- `SEM_REPORT`
- `ABSENT_LOG`
- `LATE_REPORT`
- `BREAK_LOG`
- `CONSISTENCY`

`DAILY_REPORT` displays table and visual summary but not the full insight/metric panel.

### 1.6 Student Summary Metrics (Current)
Metrics generated for student windows include:
- `real_time_attendance_rate`
- `semester_progress_attendance_rate`
- `punctuality_rate`
- `consistency_index`

Current consistency formula:
- `consistency_index = real_time_attendance_rate * 0.7 + punctuality_rate * 0.3`

Confidence model uses sample size and completeness (HIGH/MEDIUM/LOW).

### 1.7 Student Explainable Insight Engine
Student insights are generated by role-based analytics and include:
- Attendance reliability profile
- Punctuality habit pattern
- Consistency and stability signal
- Session completion behavior (early exits)
- Break discipline signal
- Previous-window trend comparison (for windowed reports)
- Evidence strength and reliability

Comparison behavior:
- Previous period metrics are computed for weekly/monthly/semestral/consistency/absent-log style windows.
- If prior comparable data is insufficient, insight output includes explicit comparison unavailability messaging.

### 1.8 Visual Summary (Student)
Student page renders:
- Status distribution bars.
- Subject-level grouped clustered bars by status.
- Trend legend and period span note.

For semestral report:
- Visual status selector is available (`ALL`, `ENTERED`, `LATE`, `ABSENT`, `BREAK_OUT`, `BREAK_IN`, `EXITED`).

### 1.9 Exported Report Output (Student)
Student can export generated table output to:
- PDF
- CSV

Export context includes:
- Report title
- Personal attendance category
- Student name + ID
- Effective report date range string

## 2) Faculty Module: Concise Required Reports

This section filters the initial report list into a practical minimum set to keep dashboards focused and maintainable.

### 2.1 Faculty Personal Attendance Records (Required)
1. Daily Attendance per Subject (`PERSONAL_DAILY`)
2. Weekly Attendance Summary (`PERSONAL_WEEKLY`)
3. Monthly Attendance Trends (`PERSONAL_MONTHLY`)
4. Semestral Report (`PERSONAL_SEMESTER`)
5. Personal Late Arrival / Instructor Delay (`INSTRUCTOR_DELAY`)
6. Personal Consistency Index (`PERSONAL_CONSISTENCY`)

Optional enhancement:
- `HISTORY_30D` as a convenience log view.

### 2.2 Faculty Class-Specific Reports (Required)
1. Class Daily Attendance (`CLASS_DAILY`)
2. Class Monthly Trends (`CLASS_MONTHLY`)
3. Class Semestral Summary (`CLASS_SEMESTER`)
4. Class Absence Summary (`CLASS_ABSENCE`)
5. Class Late Arrival Report (`CLASS_LATE`)
6. Break Duration Analysis (`BREAK_DURATION`)
7. Early Exits (`EARLY_EXITS`)
8. Punctuality Index per Section (`PUNCTUALITY_INDEX`)
9. Class Participation Consistency Insight (`PARTICIPATION_INSIGHT`)

Optional enhancement:
- `UNRECOGNIZED_LOGS`
- `BREAK_ABUSE` (derived from break-duration/no-return patterns)
- `ATTENDANCE_INCONSISTENCY`

## 3) Department Head Module: Concise Required Reports

Department Head should focus on governance and operational planning instead of duplicate low-level views.

### 3.1 Head Personal Attendance Records (Required)
Same minimum personal set as Faculty:
1. Daily Attendance per Subject
2. Weekly Attendance Summary
3. Monthly Attendance Trends
4. Semestral Report
5. Personal Late Arrival (Instructor Delay)
6. Personal Consistency Index

### 3.2 Head Department/Faculty Oversight Reports (Required)
1. Faculty Attendance Summary (`FACULTY_SUMMARY`)
2. Faculty Late Arrival Report (`FACULTY_LATE`)
3. Faculty Consistency Index (`FACULTY_CONSISTENCY`)
4. Room Occupancy Trends (`ROOM_OCCUPANCY`)
5. Peak Usage Hours (`PEAK_USAGE`)
6. Room Utilization vs Schedule (`ROOM_UTILIZATION`)
7. Overcrowding Alerts (`OVERCROWDING`)
8. Department Activity Summary (`DEPT_ACTIVITY`)

Optional enhancement:
- Additional anomaly/security-focused dashboards layered on top of existing outputs.

## 4) Implemented Envelope Contract (All Report APIs)

Current report APIs return envelope-style responses:
- `success`
- `meta`
- `summary_metrics`
- `insights`
- `rows`

Endpoints:
- Student: `/api/student/reports/data/{user_id}`
- Faculty: `/api/reports/faculty/reports/data/{user_id}`
- Department: `/api/reports/dept/reports/data`

This enables consistent frontend rendering across modules.

## 6) Notes for Future Extensions

If adding new reports:
1. Add report code to module dispatcher in `report_service.py`.
2. Return envelope-compatible rows/metrics/insights.
3. Document formula, data window, and confidence logic.
4. Keep role boundaries strict:
   - Student: self analytics
   - Faculty: class + self
   - Department Head: cross-faculty and room/ops governance.

## 7) Quick Decision Summary

If only minimum reports are enabled for demo/deployment readiness:
- Student: keep current 8 active reports.
- Faculty: enable required 6 personal + 9 class-specific.
- Department Head: enable required 6 personal + 8 oversight reports.

This preserves core academic monitoring, punctuality governance, break behavior accountability, and operational room analytics while avoiding report bloat.
